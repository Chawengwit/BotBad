# 2. Research: ข้อจำกัดที่ค้นแล้วและเปลี่ยนรูปงาน

## 2.1 บอทดึงรายชื่อสมาชิกในกลุ่มไม่ได้

`GET /v2/bot/group/{groupId}/members/ids` **ใช้ได้เฉพาะบัญชี verified หรือ premium**
บอทจ๋าเป็นบัญชีธรรมดา เรียกแล้วได้ 403

**ผลที่ตามมา:** คำสั่ง `บอทจ๋า ลงชื่อ กิ้ฟ` แปลชื่อเป็นคนไม่ได้จาก LINE
ต้องหาจากฐานข้อมูลของเราเอง ซึ่งรู้จักเฉพาะคนที่**เคยโต้ตอบกับบอทในกลุ่มนี้มาก่อน**
คนที่อยู่ในกลุ่มแต่ไม่เคยพิมพ์หาบอทเลย จะถูกลงชื่อแทนด้วยชื่อไม่ได้ (§4.4)

## 2.2 Push นับตามจำนวนคนในกลุ่ม ไม่ใช่ตามข้อความ

> "The number of messages is counted by the number of people you send a message to"
> — [Messaging API pricing](https://developers.line.biz/en/docs/messaging-api/pricing/)

ส่งเข้ากลุ่ม 30 คน = **นับ 30 ข้อความ** ส่วน Reply ที่ระบบใช้อยู่ตอนนี้**ฟรีไม่จำกัด**

**โควตาจริงของบัญชีนี้ ถามจาก LINE ตรง ๆ แล้ว ไม่ได้เดาจากบทความ**

```text
GET /v2/bot/message/quota              → {"type":"limited","value":300}
GET /v2/bot/message/quota/consumption  → {"totalUsage":0}
```

**300 ข้อความ/เดือน และยังไม่เคยใช้เลยสักข้อความ** เพราะระบบใช้ Reply ล้วนมาตลอด

จำนวนวันที่ push ได้ทั้งเดือน = `300 ÷ ขนาดกลุ่ม`

| ขนาดกลุ่ม | push ได้ (วัน/เดือน) | push สัปดาห์ละครั้ง (4.3 วัน) ใช้ไป |
| --- | --- | --- |
| 30 คน | 10 | 129 (43%) |
| 50 คน | 6 | 215 (72%) |
| ~69 คน | 4 | 297 (เพดาน) |

**ผลที่ตามมา:** push รายวันรองรับได้กลุ่มเดียวแบบเฉียดฉิว แต่ **push สัปดาห์ละครั้งรองรับได้ถึง 2 กลุ่ม กลุ่มละ 30 คน**
จึงเลือกยิงสัปดาห์ละครั้ง (§6) ไม่ใช่เพราะขี้เกียจ แต่เพราะมันเปลี่ยนฟีเจอร์นี้จาก "เฉียด" เป็น "สบาย"

## 2.3 Vercel Cron บน Hobby ทำได้ฟรี แต่เวลาไม่แม่น

| | จำนวน cron ต่อโปรเจค | ความถี่ต่ำสุด | ความแม่นของเวลา |
| --- | --- | --- | --- |
| Hobby | 100 | **วันละครั้ง** | **ต่อชั่วโมง (±59 นาที)** |

ตั้ง 10 โมงจะยิงจริงช่วง **10:00–10:59** ห้ามสัญญากับผู้ใช้ว่าตรงเวลา
"วันละครั้ง" เป็นความถี่ **สูงสุด** ตั้งรายสัปดาห์ (`0 3 * * 5`) ก็ผ่าน deploy

ของดีที่มีอยู่แล้ว: `vercel.json` ตั้ง `0 3 * * *` (UTC) = **10:00 เวลาไทยพอดี**

⚠️ แต่ **ห้ามเปลี่ยน cron ตัวนี้ไปเป็นรายสัปดาห์** เพราะหน้าที่เดิมของมันคือกัน Supabase free ถูก pause
ซึ่ง pause เมื่อไม่มีการใช้งานครบ 7 วัน — ยิงทุกวันศุกร์คือห่างกัน 7 วันพอดี บวกความคลาด ±59 นาที
แล้วอาจหลุดจนฐานข้อมูลหลับ

**ทางออกที่ยังได้ "1 cron" ตามที่สั่ง:** cron ยิงทุกวันเหมือนเดิม แต่โค้ดเช็กเองว่าวันนี้ศุกร์ไหม
ไม่ใช่ศุกร์ = แตะฐานข้อมูลแล้วจบ ไม่ push (§6.1)

## 2.4 อ่านโควตาที่ใช้ไปแล้วได้ฟรี

LINE มี endpoint บอกเพดานและยอดที่ใช้ไปของเดือนนี้ (`Get the target limit for sending messages this month`
และ `Get number of messages sent this month`) เรียกได้ไม่เสียโควตา
ใช้เป็นเบรกมือก่อน push ได้ (§6.4)

# 3. Scope

## 3.1 ทำ

- ลงชื่อ / ถอนชื่อแทนคนอื่นในกลุ่ม
- พาแขกที่ไม่มี LINE อยู่ในกลุ่มมาได้ จำชื่อแขกไว้ใช้ซ้ำข้ามรอบ
- บิลสร้างได้โดยไม่ต้องมีรอบตี
- กลุ่มหนึ่งมีบิลเปิดค้างพร้อมกันได้หลายใบ แยกกันด้วยชื่อบิล
- แต่ละรายการในบิลเลือกได้ว่าเก็บใครบ้าง
- จ่ายแทนกันได้ และระบบจำว่าใครเป็นคนจ่ายแทน
- cron สรุปเรื่องค้างเข้ากลุ่ม **ทุกวันศุกร์ 10 โมง** เฉพาะศุกร์ที่มีเรื่องจะบอก

## 3.2 ไม่ทำ พร้อมเหตุผล

| ตัดออก | เหตุผล |
| --- | --- |
| ลงชื่อแทนคนที่ไม่เคยคุยกับบอทในกลุ่มนี้ | ดึงรายชื่อสมาชิกไม่ได้ (§2.1) ให้เจ้าตัวพิมพ์ครั้งแรกเอง แล้วครั้งต่อไปลงแทนได้ |
| แขกจ่ายเงินเอง | แขกไม่มี LINE ในกลุ่ม ต้องให้คนพากดแทนเสมอ |
| เตือนเป็นรายบุคคล / ทวงตัวต่อตัว | เป็น push รายคน กินโควตาเท่ากับส่งเข้ากลุ่ม และเป็นการทวงหนี้ในนามบอท |
| บอกชื่อคนค้างจ่ายในสรุป | เจ้าของโปรเจคสั่งไว้ชัด ให้บอกแค่ว่ามีบิลค้าง คนเปิดบิลถามเองค่อยบอกชื่อ |
| สรุปทุกวัน | กินโควตา 3-4 เท่าของรายสัปดาห์ (§2.2) และก๊วนตีสัปดาห์ละครั้ง ไม่มีอะไรใหม่ให้บอกทุกวัน |
| แก้บิลหลังส่ง | เหตุผลเดิมจาก [`bill-splitting.md`](./bill-splitting.md) §4.2 ยอดของคนที่จ่ายไปแล้วจะเพี้ยน |
| ยอดค้างข้ามบิล / ledger รวม | บานปลายทันที ยังไม่มีใครขอ |

## 3.3 สิ่งที่ต้องยอมรับ

1. สรุปมาถึงช่วง 10:00–10:59 ของวันศุกร์ ไม่ตรงเป๊ะ
2. เรื่องที่เกิดวันเสาร์ จะถูกพูดถึงในศุกร์ถัดไปเท่านั้น — อยากรู้ก่อนต้องพิมพ์ถามเอง (ฟรี)
3. ฟีเจอร์นี้มีเพดานตามโควตาฟรีของ LINE ไม่ใช่ของเราเอง
4. แขกเป็นแค่ชื่อในระบบ ยืนยันตัวตนไม่ได้ ใครพิมพ์ชื่ออะไรก็เป็นแขกได้

# 4. คนและแขก

## 4.1 เก็บแขกไว้ที่ไหน

**เก็บแขกเป็นแถวใน `users` ที่ `line_user_id` เป็น NULL**

เหตุผล: `game_players` และ `bill_shares` join `users` อยู่แล้วทุก query
ถ้าแยกตาราง `guests` ต้องทำให้สองตารางนั้นมีสองคอลัมน์ (`user_id` หรือ `guest_id`)
แล้วต้องแก้ทุก JOIN, ทุก UNIQUE และทุก service ที่แตะผู้เล่น — ได้ความสะอาดบนกระดาษ แลกกับงานทั้งระบบ

| ชนิด | `line_user_id` | `line_group_id` |
| --- | --- | --- |
| สมาชิก LINE | มีค่า | NULL (คนเดียวอยู่ได้หลายกลุ่ม) |
| แขก | NULL | มีค่า (แขกผูกกับกลุ่มที่พามา) |

แขกชื่อซ้ำในกลุ่มเดียวกันไม่ได้ → `UNIQUE (line_group_id, display_name) WHERE line_user_id IS NULL`
ทำให้ "ฮกพากิ้ฟมาทุกอาทิตย์" ใช้แถวเดิมทุกครั้ง ไม่งอกแถวใหม่ และประวัติการจ่ายเงินตามตัวไปด้วย

## 4.2 ใครลงชื่อให้

เพิ่ม `game_players.added_by` → NULL คือลงเอง มีค่าคือคนที่ลงให้

ใช้ได้ทั้งกับแขกและกับสมาชิกจริง ไม่ต้องแยกกลไก

## 4.3 สิทธิ์ถอนชื่อ

**เจ้าตัว หรือคนที่ลงชื่อให้ เท่านั้น**

```text
ฮกพากิ้ฟมา   → ฮกถอนกิ้ฟได้ คนอื่นถอนไม่ได้
ฮกลงให้แบงค์  → แบงค์ถอนเองก็ได้ ฮกถอนให้ก็ได้ คนอื่นถอนไม่ได้
```

เหตุผลที่ไม่เปิดให้ใครถอนใครก็ได้: ก๊วนเชื่อใจกันก็จริง แต่กดผิดแล้วคนหายจากรอบโดยไม่มีใครรู้ตัว
ส่วนคนเปิดรอบไม่ได้สิทธิ์พิเศษตรงนี้ เพราะไม่ได้เป็นคนพาเขามา

ผิดเงื่อนไข → `NOT_YOUR_GUEST`

> เปลี่ยนแล้ว (2026-09-19): แชทจริงพิมพ์ "บอทจ๋า ยังไม่ให้ louis ตีแบด น่าสงสารขนาดไหน 555"
> บอทตอบว่าถอน louis ให้แล้ว ทั้งที่รอบยังไม่มีใครลงชื่อและไม่มีใครชื่อ louis
> - เช็กตามลำดับ: มีรอบเปิดอยู่ → ชื่ออยู่ในรายชื่อรอบนี้ → คนสั่งมีสิทธิ์ถอน
> - ไม่อยู่ในรายชื่อ (ไม่รู้จักชื่อ หรือรู้จักแต่ไม่ได้ลง) → `ℹ️ louis ไม่ได้อยู่ในรายชื่อรอบนี้`
> - สั่งเป็นประโยคให้ถอนคนอื่น ต้องกดยืนยันก่อน (`leave_players`) คำสั่งพิมพ์ยังถอนทันที
> - ลงชื่อ / ถอนชื่อ / จ่ายเงิน ผ่านประโยค ตอบด้วยข้อความของระบบอย่างเดียว ไม่ส่งข้อความที่ LLM แต่ง

## 4.4 แปลชื่อเป็นคน

ลำดับการค้นเมื่อเจอ `บอทจ๋า ลงชื่อ กิ้ฟ`

```text
1. แขกของกลุ่มนี้ที่ชื่อตรงกัน                    → ใช้แถวเดิม
2. สมาชิกที่เคยลงชื่อในรอบของกลุ่มนี้ ชื่อตรงกัน   → ใช้คนนั้น
3. ชื่อตรงกันหลายคน                              → ถามกลับว่าหมายถึงใคร
4. ไม่เจอเลย                                     → ถามยืนยันว่าจะเพิ่มเป็นแขกใหม่ไหม
```

ข้อ 4 ต้องถามก่อนเสมอ ไม่งั้นพิมพ์ผิดทีเดียวได้แขกผีเพิ่มถาวร

เทียบชื่อแบบตัดช่องว่างหัวท้ายและไม่สนตัวพิมพ์เล็กใหญ่ ไม่ทำ fuzzy match
เพราะเดาผิดเรื่องคนแย่กว่าถามซ้ำ

## 4.5 แขกนับในจำนวนคนของรอบ

แขกกินคอร์ทจริง จึงนับรวมใน `max_players` ทุกที่ ไม่มีข้อยกเว้น

## 4.6 คำสั่ง

| คำสั่ง | ผล |
| --- | --- |
| `ลงชื่อ` | ลงชื่อตัวเอง (เหมือนเดิม) |
| `ลงชื่อ กิ้ฟ วิท` | ลงชื่อให้สองคน `added_by` = คนพิมพ์ |
| `ถอนชื่อ` | ถอนตัวเอง (เหมือนเดิม) |
| `ถอนชื่อ กิ้ฟ` | ถอนคนที่ตัวเองลงให้ |

⚠️ กระทบ spec §18: ตอนนี้ rule command เทียบแบบ **ตรงทั้งข้อความ**
ต้องเพิ่มแนวคิด "คำสั่งที่รับส่วนเติมท้าย" ใน `src/router/rule-commands.ts` (§8)

## 4.7 บอทต้องประกาศให้เห็น

ลงหรือถอนแทนกัน ข้อความตอบต้องบอกชัดว่าใครทำให้ใคร ไม่ใช่ขึ้นแค่ชื่อคนถูกลง

```text
✅ ฮก ลงชื่อให้ กิ้ฟ, วิท
👥 7/16 คน
```

# 5. บิล v2

## 5.1 อะไรเปลี่ยนจากของเดิม

| ที่ขอ | ของเดิมสมมติว่า | ต้องแก้ |
| --- | --- | --- |
| บิลแยกจากรอบ | `bills.game_id NOT NULL`, `line_group_id` มาจาก JOIN `games` | `game_id` nullable + เพิ่ม `bills.line_group_id` |
| หลายบิลพร้อมกัน | `findActiveBill` คืนบิลล่าสุดใบเดียวของกลุ่ม | เพิ่ม `bills.title` + คำสั่งระบุชื่อบิลได้ |
| แยกเก็บรายคน | `splitEqually` หารเท่ากันทุกรายการ | `items` jsonb → ตาราง `bill_items` + `bill_item_payers` |
| จ่ายแทนกัน | `bill_shares` เป็นสถานะของเจ้าตัว | เพิ่ม `bill_shares.paid_by` |

## 5.2 ชื่อบิล

ทุกบิลมีชื่อ ตั้งตอนสร้าง ห้ามซ้ำกับบิลที่ยังเปิดอยู่ของกลุ่มเดียวกัน

```text
บอทจ๋า คิดเงิน               → บิลของรอบที่เปิดอยู่ ชื่อตั้งให้เอง "รอบ พุธ 16 ก.ย."
บอทจ๋า คิดเงิน ค่ากินข้าว     → บิลลอย ๆ ไม่ผูกกับรอบ
```

> เปลี่ยนแล้ว: `บอทจ๋า คิดเงิน` เฉย ๆ ขึ้นการ์ดให้เลือกก่อน คิดค่ารอบ / สร้างบิลใหม่ / แก้บิลเดิม
> เพราะเดาว่าเป็นค่ารอบทำให้คนที่อยากสร้างบิลอื่นติดอยู่ที่คำถามค่าคอร์ท (spec §23 คิดเงิน)

คำสั่งที่ทำกับบิลระบุชื่อต่อท้ายได้ **ถ้ามีบิลเปิดอยู่ใบเดียวไม่ต้องระบุ**

```text
บอทจ๋า บิล                   → ใบเดียว: แสดงใบนั้น | หลายใบ: แสดงรายการให้เลือก
บอทจ๋า บิล ค่ากินข้าว         → เจาะจงใบนั้น
บอทจ๋า จ่ายแล้ว ค่ากินข้าว
```

มีหลายใบแล้วไม่ระบุชื่อ → `BILL_AMBIGUOUS` พร้อมรายชื่อบิลที่เปิดอยู่

> เปลี่ยนแล้ว: ไม่ระบุชื่อบิล บอทเลือกเฉพาะใบที่คำสั่งนั้นมีอะไรให้ทำ บิลที่ยกเลิกหรือทุกคนจ่ายครบแล้วถือว่าจบ
> เพราะแชทจริง (2026-09-18) พิมพ์ "วิทจ่ายแล้ว" บอทถามว่าหมายถึงใบไหน ทั้งที่อีกใบวิทจ่ายไปแล้วและทุกคนจ่ายครบแล้ว
>
> | คำสั่ง | ใบที่เลือกได้ | ไม่เหลือใบไหนเลย |
> | --- | --- | --- |
> | `จ่ายแล้ว` | ใบที่คนในคำสั่งยังค้าง | `NOTHING_OWED` |
> | `ยังไม่จ่าย` | ใบที่เคยบันทึกว่าคนในคำสั่งจ่ายแล้ว รวมใบที่ครบแล้ว (ย้อนคนสุดท้ายที่กดผิดได้) | `NOTHING_PAID` |
> | `บิล` / `ใครยังไม่จ่าย` | ใบที่ยังมีคนค้าง | `ALL_BILLS_SETTLED` |
> | `ยกเลิกบิล` | ทุกใบที่เปิดอยู่ | – |
>
> เหลือใบเดียวใช้เลยไม่ต้องถาม หลายใบ → `BILL_AMBIGUOUS` เสนอเฉพาะใบที่เลือกได้
> ระบุชื่อบิลมา = ใบนั้นเสมอ แม้ทุกคนจะจ่ายครบแล้ว
> คนที่อยู่ในสถานะนั้นอยู่แล้ว (บอกจ่ายซ้ำ) ไม่นับว่าเพิ่งจ่าย ขึ้นแยกบรรทัดว่าจ่ายไปแล้ว

## 5.2.1 เลขพร้อมเพย์ย้ายมาอยู่ที่บิล

การ์ดบิลตอนนี้อ่านเลขพร้อมเพย์จาก `games.promptpay` ตรง ๆ ซึ่งใช้กับบิลลอย ๆ ไม่ได้เพราะไม่มีรอบ

ถ้าให้บิลลอย ๆ ไปหยิบเลขล่าสุดของกลุ่มมาใช้ (`findLatestPromptPay`) จะเกิดเรื่องนี้:
**ฮกสร้างบิล "ค่ากินข้าว" แต่การ์ดขึ้นเลขพร้อมเพย์ของเชวง** เพราะเชวงเป็นคนเปิดรอบครั้งก่อน — เงินไปผิดคน

จึงเพิ่ม `bills.promptpay` แล้ว **ถามคนสร้างบิลเสมอ** โดยเสนอเลขที่ตัวเขาเองเคยใช้เป็นตัวเลือกแรก
ไม่ใช่เลขล่าสุดของกลุ่ม

การ์ดบิลต้องขึ้นชื่อคนรับโอนด้วย ไม่ใช่มีแต่ตัวเลข:

```text
💸 โอนให้ ฮก · 081-234-5678
```

บิลของรอบตียังใช้เลขจาก `games.promptpay` เป็นค่าตั้งต้นได้ตามเดิม แต่คัดลอกลง `bills.promptpay` ตอนสร้าง
เพื่อให้บิลที่ออกไปแล้วไม่เปลี่ยนตามการแก้รอบทีหลัง

## 5.3 รายการและคนร่วมจ่าย

แต่ละรายการมีรายชื่อคนร่วมจ่ายของตัวเอง ไม่ระบุ = ทุกคนในบิล

รูปแบบที่พิมพ์: `<ชื่อรายการ> <จำนวนเงิน> [ชื่อคน ...]`

```text
ค่าคอร์ท 600              → เก็บทุกคนในบิล
ค่าน้ำ 60 เชวง แบงค์       → เก็บสองคนนี้
```

จำนวนเงินเป็นตัวคั่นระหว่างชื่อรายการกับชื่อคน
`parseOtherItem` ปัจจุบันใน `src/services/bill.service.ts` ใช้ regex ที่คาดว่าเลขอยู่ท้ายสุด ต้องเขียนใหม่

ชื่อคนแปลด้วยกติกาเดียวกับ §4.4 ทุกประการ

## 5.4 ใครอยู่ในบิล

- บิลของรอบตี → คนที่ `status = 'joined'` ตอนกดยืนยัน (snapshot เหมือนเดิม)
- บิลลอย ๆ → คนที่ถูกเอ่ยชื่อในรายการใดรายการหนึ่ง

ไม่มีใครอยู่ในบิลเลย → `NO_PLAYERS_TO_SPLIT` (code เดิม)

## 5.5 การหารและเศษสตางค์

หาร **รายรายการ** ไม่ใช่หารยอดรวม

```text
ยอดของคน X = ผลรวมของ (รายการ ÷ จำนวนคนร่วมจ่ายของรายการนั้น) ทุกรายการที่ X ร่วมจ่าย
```

เศษของแต่ละรายการตกที่ **คนสร้างบิล** ถ้าเขาร่วมจ่ายรายการนั้น ไม่งั้นตกที่คนแรกของรายการนั้น
(กติกาเดียวกับ [`bill-splitting.md`](./bill-splitting.md) §5.3 แค่ย้ายจากระดับบิลมาระดับรายการ)

**Invariant ที่ต้องมีเทส:** `SUM(bill_item_payers.amount) = bills.total_satang`
และ `SUM(bill_shares.amount) = bills.total_satang`

## 5.6 จ่ายแทนกัน

```text
บอทจ๋า จ่ายแล้ว              → ของตัวเอง
บอทจ๋า จ่ายแล้ว กิ้ฟ วิท      → ของตัวเองด้วยไหม? ไม่ — เฉพาะสองคนนี้
บอทจ๋า จ่ายแล้ว ฉัน กิ้ฟ วิท   → ทั้งสามคน
```

เก็บ `bill_shares.paid_by` ไว้ว่าใครเป็นคนบอก

> เพิ่มแล้ว: ระบุทั้งคนและบิลในคำสั่งเดียว `บอทจ๋า จ่ายแล้ว วิท ร้านโชคดี`
> เทียบท้ายข้อความกับชื่อบิลที่เปิดอยู่ (ชื่อบิลมีช่องว่างได้ เลือกชื่อที่ยาวที่สุดที่ตรง) ที่เหลือเป็นรายชื่อคน
> เดิมอ่านทั้งหมดเป็นรายชื่อคน ถ้าวิทค้างหลายบิลจะพิมพ์คำสั่งให้จบไม่ได้

**ใครกดแทนใครได้:** เจ้าตัว, คนที่พาแขกคนนั้นมา, และคนสร้างบิล
คนสร้างบิลได้สิทธิ์ตรงนี้เพราะเป็นคนรับโอน มีคนจ่ายเงินสดให้ตรง ๆ ได้

⚠️ ต่างจาก [`bill-splitting.md`](./bill-splitting.md) §4.2 ที่เคยตัด "กดแทนคนอื่น" ทิ้ง
เหตุผลเดิมคือ "คนจ่ายอยู่ในกลุ่มและกดเองได้" ซึ่งไม่จริงอีกต่อไปเมื่อมีแขก

## 5.7 การ์ดบิลเปลี่ยนหน้าตา

ของเดิมขึ้น "คนละ 95.00" ได้เพราะทุกคนเท่ากัน ตอนนี้ต้องขึ้นยอดรายคน

```text

🏟️ ค่าคอร์ท              600.00   ทุกคน
💧 ค่าน้ำ                  60.00   เชวง, แบงค์
──────────
รวม                      660.00

💸 โอนให้ เชวง · 081-234-5678

เชวง      180.00   ✅
แบงค์     180.00   ⭕
ฮก        150.00   ⭕  (รวม กิ้ฟ, วิท)
```

คนที่พาแขกมาเห็นยอดรวมของตัวเองกับแขก เพราะเป็นคนโอนจริง

# 6. สรุปประจำสัปดาห์ (cron)

## 6.1 เวลาและที่มา

**ทุกวันศุกร์ ช่วง 10:00–10:59 ตามเวลาไทย**

ใช้ cron ตัวเดิมใน `vercel.json` (`0 3 * * *` UTC = 10:00 ไทย) **ยิงทุกวันเหมือนเดิม ไม่แก้ schedule**
ย้าย endpoint จาก `/api/health` ไป `/api/cron/daily` แล้วให้ตัดสินใจเองในโค้ด

```text
ทุกวัน   → แตะฐานข้อมูล (กัน Supabase pause) แล้วจบ
วันศุกร์  → แตะฐานข้อมูล + ประเมินทุกกลุ่ม + push กลุ่มที่มีเรื่องจะบอก
```

ยิงทุกวันแต่ push เฉพาะศุกร์ ได้ครบสามอย่าง: กัน Supabase หลับ, ประหยัดโควตา, และยังมี cron แค่ตัวเดียว

`/api/health` ยังอยู่ไว้เช็กสุขภาพด้วยมือ แต่ไม่มี cron เรียกแล้ว

วันในสัปดาห์ต้องคิดตามเวลาไทย ไม่ใช่ UTC — ใช้ `todayInBangkok()` ใน `src/lib/time.ts` ที่มีอยู่แล้ว

## 6.2 บอกอะไรบ้าง

| เรื่อง | เงื่อนไข | ข้อความ |
| --- | --- | --- |
| รอบที่เปิดอยู่ | มีรอบ `status = 'open'` | ทุกรอบ วัน เวลา คอร์ท และจำนวนคนที่ลงแล้ว — **ไม่ว่าจะตีวันไหน** |
| ~~รอบค้างเก่า~~ | ~~รอบ `open` ที่วันเล่นผ่านไปแล้ว~~ | ตัดออกแล้ว รอบพวกนี้ถูกปิดอัตโนมัติทุกเช้า (PRP multi-open-rounds §5) |
| บิลค้าง | มีบิล `sent` ที่ยังมีคนไม่จ่าย | **จำนวนบิลและยอดรวมที่ยังไม่ได้รับ ห้ามบอกชื่อคน** |
| ไม่มีอะไรเลย | — | **ไม่ push** |

ยิงสัปดาห์ละครั้งจึงเตือนแบบ "พรุ่งนี้มีนัด" ไม่ได้ เพราะจะเตือนได้แต่รอบที่ตีวันเสาร์
ก๊วนที่ตีวันพุธจะไม่เคยได้รับอะไรเลย — ข้อความจึงพูดถึง **รอบที่เปิดค้างอยู่ตอนนี้** แทน

ตัวอย่าง

```text
☀️ สรุปประจำสัปดาห์

🏸 มีนัด — พุธ 22 ก.ย. 19:00-21:00 ที่ ABC Badminton
👥 ลงชื่อแล้ว 6/24 คน

💰 มีบิลค้างอยู่ 1 ใบ ยังไม่ได้รับ 507.00
   คนเปิดบิลพิมพ์ "บอทจ๋า ใครยังไม่จ่าย" เพื่อดูรายชื่อ
```

ศุกร์ไหนไม่มีรอบเปิดและไม่มีบิลค้าง → **เงียบสนิท ไม่ push**
ไม่ชวนเปิดรอบ ไม่ทักทาย เพราะข้อความที่ไม่มีเนื้อหาคือข้อความที่คนเริ่มไม่อ่าน

## 6.3 ส่งซ้ำไม่ได้

cron ยิงซ้ำได้ (retry, deploy ซ้ำ) ต้องกันไม่ให้กลุ่มได้สรุปสองรอบในศุกร์เดียว
เก็บ `group_digests(line_group_id, last_sent_on DATE)` แล้วเช็กก่อนส่งทุกครั้ง

## 6.4 เบรกมือกันโควตาบาน

ก่อนส่ง เรียก endpoint อ่านโควตาของ LINE (§2.4) แล้วหยุดถ้าใช้ไปเกินเพดานที่ตั้งไว้

```text
PUSH_QUOTA_STOP_AT   สัดส่วนที่ใช้ไปแล้วจะหยุด push (ค่าเริ่มต้น 0.8)
```

ที่ขนาดกลุ่มปัจจุบันยังห่างเพดานมาก (§2.2) แต่เบรกนี้มีไว้เผื่อบอทไปอยู่หลายกลุ่มโดยไม่มีใครคำนวณใหม่

หยุดแล้วต้อง log ให้ดัง ไม่ใช่เงียบ เพราะคนในกลุ่มจะไม่รู้เลยว่าทำไมสรุปหาย

## 6.5 ความล้มเหลวต้องไม่ลาม

กลุ่มหนึ่ง push ไม่ผ่านต้องไม่ทำให้กลุ่มที่เหลือไม่ได้รับ
วนทีละกลุ่ม จับ error รายกลุ่ม แล้วคืน 200 เสมอ (คนละกติกากับ webhook แต่เหตุผลเดียวกัน)

## 013 — บิล v2

```sql
ALTER TABLE bills ADD COLUMN line_group_id TEXT;
UPDATE bills SET line_group_id = (SELECT g.line_group_id FROM games g WHERE g.id = bills.game_id);
ALTER TABLE bills ALTER COLUMN line_group_id SET NOT NULL;
ALTER TABLE bills ALTER COLUMN game_id DROP NOT NULL;

ALTER TABLE bills ADD COLUMN title TEXT NOT NULL DEFAULT '';
UPDATE bills SET title = 'บิลรอบเก่า ' || id WHERE title = '';

-- เลขพร้อมเพย์ของบิลเอง บิลลอย ๆ ไม่มีรอบให้ดึง (§5.2.1)
ALTER TABLE bills ADD COLUMN promptpay TEXT;
ALTER TABLE bills ADD CONSTRAINT bills_promptpay_check
  CHECK (promptpay IS NULL OR promptpay ~ '^([0-9]{10}|[0-9]{13})$');
UPDATE bills SET promptpay = (SELECT g.promptpay FROM games g WHERE g.id = bills.game_id);

CREATE UNIQUE INDEX uq_bills_open_title
  ON bills (line_group_id, title)
  WHERE status = 'sent';

-- เลิกบังคับ 1 รอบ 1 บิล รอบหนึ่งมีได้ทั้งค่าคอร์ทและค่ากินข้าว
DROP INDEX uq_bills_one_active_per_game;

CREATE TABLE bill_items (
  id                 BIGSERIAL PRIMARY KEY,
  bill_id            BIGINT NOT NULL REFERENCES bills(id) ON DELETE CASCADE,
  position           INT NOT NULL,
  label              TEXT NOT NULL,
  quantity           INT NOT NULL DEFAULT 1 CHECK (quantity > 0),
  unit_price_satang  BIGINT NOT NULL CHECK (unit_price_satang >= 0),
  amount_satang      BIGINT NOT NULL CHECK (amount_satang > 0),
  UNIQUE (bill_id, position)
);

CREATE TABLE bill_item_payers (
  bill_item_id   BIGINT NOT NULL REFERENCES bill_items(id) ON DELETE CASCADE,
  user_id        BIGINT NOT NULL REFERENCES users(id),
  amount_satang  BIGINT NOT NULL CHECK (amount_satang >= 0),
  PRIMARY KEY (bill_item_id, user_id)
);

-- ใครเป็นคนบอกว่าจ่ายแล้ว NULL = เจ้าตัวบอกเอง
ALTER TABLE bill_shares ADD COLUMN paid_by BIGINT REFERENCES users(id);
```

**`items` jsonb เดิมเก็บไว้ก่อน** ไม่ต้อง drop จนกว่าจะมั่นใจว่าบิลเก่าอ่านผ่านทางใหม่ได้หมด
เหตุผลที่ย้ายจาก jsonb มาเป็นตาราง: [`bill-splitting.md`](./bill-splitting.md) §11 บอกว่า
"ไม่เคย query ทีละรายการ" ซึ่งไม่จริงอีกต่อไปเมื่อแต่ละรายการมีรายชื่อคนของตัวเอง

| --- | --- |

# 8. Router และคำสั่ง

## 8.1 คำสั่งที่รับส่วนเติมท้าย

| รูปแบบ | ตัวอย่าง |
| --- | --- |
| `ลงชื่อ <ชื่อ ...>` | `บอทจ๋า ลงชื่อ กิ้ฟ วิท` |
| `ถอนชื่อ <ชื่อ ...>` | `บอทจ๋า ถอนชื่อ กิ้ฟ` |
| `จ่ายแล้ว <ชื่อ ...>` | `บอทจ๋า จ่ายแล้ว กิ้ฟ วิท` |
| `ยังไม่จ่าย <ชื่อ ...>` | |
| `คิดเงิน <ชื่อบิล>` | `บอทจ๋า คิดเงิน ค่ากินข้าว` |
| `บิล <ชื่อบิล>` | |
| `ยกเลิกบิล <ชื่อบิล>` | |

ไม่มีส่วนเติม = พฤติกรรมเดิมทุกประการ ของเก่าต้องไม่พังแม้แต่คำสั่งเดียว

## 8.2 Postback ที่เพิ่ม

```text
action=wizard&pending_id=<uuid>&step=item_payers&value=...
```

wizard คิดเงินต้องมีขั้นถามว่ารายการนี้เก็บใคร ตอบด้วยการพิมพ์ (`awaiting`) แบบเดียวกับชื่อคอร์ท

## 8.3 ปุ่ม

ยึด spec §23 เดิม: แนบปุ่มเฉพาะตอนถาม ตอนขอยืนยัน และเมนู
การ์ดบิลใหม่ยังเป็นข้อความล้วนเหมือนเดิม

## 9.1 Tool ที่เปลี่ยน

## 9.2 Rules ที่ต้องแก้

**R16 ปัจจุบันขัดกับฟีเจอร์นี้ตรง ๆ**

> R16. ห้ามทำรายการแทนสมาชิกคนอื่น tool จะทำกับคนที่พิมพ์ข้อความเท่านั้น

ต้องเขียนใหม่เป็น: ทำแทนได้เมื่อผู้ใช้ระบุชื่อมาชัดเจน แต่ห้ามเดาชื่อเอง
และห้ามลงชื่อคนที่ผู้ใช้ไม่ได้เอ่ยถึง

เพิ่มกติกา: ถ้าชื่อที่ได้มากำกวมหรือไม่เคยเจอ ให้ถามกลับ ห้ามสร้างแขกใหม่เงียบ ๆ

# 16. Definition of Done

```text
ฮก:     บอทจ๋า ลงชื่อ กิ้ฟ วิท
บอท:    ✅ ฮก ลงชื่อให้ กิ้ฟ, วิท — 👥 7/16 คน

(ตีเสร็จ)

เชวง:   บอทจ๋า คิดเงิน
บอท:    ค่าคอร์ทเท่าไหร่? → ... → มีค่าอื่นอีกไหม?
เชวง:   ค่าน้ำ 60 เชวง แบงค์
บอท:    [การ์ดบิล — ค่าคอร์ทเก็บทุกคน ค่าน้ำเก็บสองคน ยอดรายคนไม่เท่ากัน]

ฮก:     บอทจ๋า จ่ายแล้ว ฉัน กิ้ฟ วิท
บอท:    ✅ บันทึกแล้ว ฮก จ่าย 450.00 (รวม กิ้ฟ, วิท) — เหลืออีก 4 คน

(ศุกร์ถัดมา 10 โมง)

บอท:    ☀️ สรุปประจำสัปดาห์
        🏸 มีนัด — พุธ 22 ก.ย. 19:00-21:00 ที่ ABC Badminton
        💰 มีบิลค้างอยู่ 1 ใบ ยังไม่ได้รับ 507.00
```

และต้องจริงด้วยว่า:

- ศุกร์ที่ไม่มีรอบและไม่มีบิลค้าง กลุ่มต้องเงียบสนิท
- วันที่ไม่ใช่ศุกร์ ต้องไม่ push แม้มีเรื่องค้างอยู่
- ฐานข้อมูลต้องถูกแตะทุกวัน ไม่ใช่เฉพาะศุกร์ (กัน Supabase หลับ)
- คำสั่งเดิมทุกคำสั่งทำงานเหมือนเดิมทุกประการ
- บิลที่สร้างไว้ก่อน migration ยังอ่านและจ่ายได้
